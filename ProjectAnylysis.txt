1. project idea

Build a small e-commerce order system.

User flow:

User registers/login
User views products
User adds products to cart
User places order
Inventory is reserved
Payment is processed
Order is confirmed
Notification is generated
If payment fails, stock is released

This gives you real practical understanding of microservices.

4. RabbitMQ Event Flow
Successful order flow
1. User places order
2. Order Service saves order as Pending
3. Order Service publishes OrderCreatedEvent
4. Inventory Service consumes OrderCreatedEvent
5. Inventory Service reserves stock
6. Inventory Service publishes StockReservedEvent
7. Payment Service consumes StockReservedEvent
8. Payment Service processes payment
9. Payment Service publishes PaymentCompletedEvent
10. Order Service consumes PaymentCompletedEvent
11. Order status becomes Confirmed
12. Notification Service sends confirmation message
Failed payment flow
1. User places order
2. Inventory is reserved
3. Payment fails
4. Payment Service publishes PaymentFailedEvent
5. Order Service marks order as Failed
6. Inventory Service releases reserved stock
7. Notification Service sends payment failed message

This is where you practically learn Saga Pattern and Distributed Transactions.

9. Saga Pattern Practical Flow

Use Order Service as Saga Orchestrator.

Order status flow:

Pending
StockReserved
PaymentCompleted
Confirmed
Failed
Cancelled

Example:

OrderCreated
   |
   v
Reserve Stock
   |
   |-- Success --> Process Payment
   |                  |
   |                  |-- Success --> Confirm Order
   |                  |
   |                  |-- Failed --> Release Stock + Cancel Order
   |
   |-- Failed --> Cancel Order

This is very useful for interviews because you can explain:

We do not use one database transaction across services.
Each service owns its database.
We coordinate using events.
If one step fails, we use compensating action.
This is called Saga Pattern.

16. Final Interview Explanation

You can explain this project like this:

I created a SmartCart microservices-based order management system using ASP.NET Core Web API. 
The system has separate services for Identity, Catalog, Cart, Orders, Inventory, Payments, and Notifications. 
Each service owns its own SQL Server database, following the Database Per Service pattern. 
YARP is used as an API Gateway and JWT is used for authentication. 
Redis is used for cart storage and product caching. 
RabbitMQ is used for asynchronous communication between services. 
The order flow uses Saga Pattern to handle distributed transactions between Order, Inventory, and Payment services. 
CQRS is implemented using MediatR, FluentValidation is used for request validation, and AutoMapper is used for DTO mapping. 
Docker is used for local containerization, Kubernetes is used for orchestration, and the system can be deployed to Azure using AKS or Azure Container Apps.

PostgreSQL Database Per Service Design

Use separate database for each microservice.

identity_db
catalog_db
cart_db
order_db
inventory_db
payment_db
notification_db

Important microservice rule:

Do not create foreign keys between different service databases.
Use IDs only, like user_id, product_id, order_id.
Each service owns its own database.

8. API Gateway DB

For YARP API Gateway, no database is required.

API Gateway only handles:

Routing
JWT validation
Reverse proxy
Rate limiting optional
Logging optional

YARP is Microsoft’s .NET reverse proxy toolkit; use the official dotnet/yarp / microsoft/reverse-proxy project.
